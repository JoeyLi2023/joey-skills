# 文件类型与使用合约

**使用方式**：Step 2 读取，帮助用户对每个步骤所需的知识分类，从而确定需要哪些文件。

---

## 核心原则

Skill 里的 references/ 文件不是按"内容主题"分的，而是按**使用时机**分的。同一个主题的知识，如果在流程的不同时刻使用，就应该拆成不同的文件。

SKILL.md 是工作流的"宪法"——它决定每个步骤读哪个文件。其他文件的边界，由它在工作流中的位置决定。

---

## 四种文件类型

### 类型一：选择锁死型

**特征**：读一次，做一个选择，锁死，后续步骤基于这个选择展开。

**最佳形式**：
- 列出所有选项，每个选项有：名称 / 适用场景 / 禁止用于
- 明确推荐默认值（或说明如何选）
- 写清楚"选完之后后续有何不同"

**典型例子**：PRD 类型（新功能/MVP/迭代增强）、PPT 主题色

**Anti-pattern**：给了太多自由度——如果什么都能选、什么都可以混，这个文件就没有起到"锁定"的作用。好的选择锁定文件应该有"不允许自定义"的硬规定。

---

### 类型二：骨架套用型

**特征**：根据已锁定的选择，挑一个对应骨架，直接复制填写，用完即放。

**最佳形式**：
- 每种情况对应一套完整骨架，直接可粘贴
- 骨架里用 `{占位符}` 标注需要填写的内容
- 附上"哪些章节可省略"的说明

**典型例子**：PRD 章节骨架（S1-S6）、PPT 页面布局（Layout 1-10）

**Anti-pattern**：骨架太泛，像个通用模板，用什么需求都要大幅修改。好的骨架是"七八成已经填好，只需要改具体内容"。

---

### 类型三：字典查阅型

**特征**：在内容填写过程中，遇到特定问题时翻查，查完即放，可能被多次查阅。

**最佳形式**：
- 从"用户会问什么问题"出发，而不是从"知识点分类"出发
- 好的例子 + 坏的例子对比（坏的例子更有价值）
- 有"禁止区"——把最常见的错误写成硬性禁止

**典型例子**：写作规范（criteria.md）、成功指标参考（metrics.md）、默认规则表（defaults.md）

**Anti-pattern**：写成"全面指南"——面面俱到但没有重点。字典文件的价值在于查到具体问题立刻有答案，而不是让人通读。

---

### 类型四：验收检查型

**特征**：在任务完成后，逐条核对，不通过则返工。

**最佳形式**：
- 按严重程度分级（P0 废稿级 / P1 明显问题 / P2 最好有）
- 每条检查项说明"违反了会导致什么"——知道后果才知道为什么要查
- P0 项必须来自真实踩坑，不能是理论上的

**典型例子**：PRD 质量清单（checklist.md）、PPT 生成前检查清单

**Anti-pattern**：P0 太多，全是 P0 等于没有优先级。真正的 P0 应该是"这条不过，整个输出作废"。

---

## 使用合约格式

每个 references/ 文件开头必须写清楚：

```
本文件类型：[选择锁死 / 骨架套用 / 字典查阅 / 验收检查]
读取时机：Step N，[做什么决策/查什么信息]
读后处理：[读完即放 / 持续参考 / 最后一次性使用]
```

---

## 种子文件（assets/）

种子文件不是 references，它是一个**可以直接运行的起始文件**（HTML 模板、Markdown 模板、配置文件等）。

**核心原则**：把所有约束物化进去。能写进种子文件的规则，就不要只写在说明文字里。

**什么情况下需要种子文件**：
- 输出有固定结构，且结构本身很复杂（如 HTML + CSS + JS）
- 有大量预置内容，AI 只需要填局部（不需要从零生成）
- 存在"类名/变量/格式必须和其他部分完全匹配"的强约束

**什么情况下不需要**：任务的输出每次都差异很大，或者没有可复用的起始结构。
