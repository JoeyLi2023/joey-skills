# UI 设计决策指南

## 核心原则

### 1. 信息层级决定视觉权重

每个页面的输入项/内容块必须有明确的优先级排序。视觉权重要匹配信息重要程度：

- **主要内容**（如核心输入框）：最大面积、最少装饰、最显眼位置
- **次要内容**（如辅助输入）：始终可见但紧凑，不抢主角风头
- **可选/高级内容**（如配置项）：默认隐藏，通过按钮/折叠/弹窗按需展开

**反模式**：所有输入项线性堆叠、视觉重量相同、没有主次之分。

### 2. 渐进展示（Progressive Disclosure）

不要一次性把所有选项摊开。用户大多数时候只需要核心功能，高级选项应该：
- 收在工具栏按钮后面（如「补充说明」）
- 放在 Popover/下拉中（如「设置」）
- 用折叠面板展开（如「高级配置」）

但要在入口处暗示内容的存在（如状态 chip 显示「8 个问题 · 含原型」）。

### 3. Composer 模式 vs 表单模式

当页面核心是「一段文字输入 + 若干辅助项」时，**优先用 Composer 模式**：

```
┌─────────────────────────────────┐
│  大文本输入区（无边框，融入背景）    │
│                                 │
│                                 │
├─────────────────────────────────┤
│  次要输入（紧凑的横向排列）         │
├─────────────────────────────────┤
│ [补充说明] | [设置]    [状态] [提交]│
└─────────────────────────────────┘
```

而不是传统表单模式：
```
标题
[输入框]
标题
[输入框]
标题
[输入框]
[提交按钮]
```

### 4. 紧凑优于铺张

次要元素用紧凑表达：
- 图片上传：小缩略图横排（56×56px） + 「附图」按钮，而不是大的拖拽区域
- 配置项：Popover 里的开关/数字输入，而不是占满一行的 checkbox
- 状态提示：一个小 chip（「8 个问题 · 含原型」），而不是独立的说明段落

## 工作流程

### 第一步：分析现有问题

拿到用户的页面截图或代码后，先指出具体问题：
- 哪些元素的视觉权重不匹配其重要程度？
- 哪些可选项不必要地占用了核心空间？
- 整体布局是否有主次之分？

### 第二步：提出多方案

给出 2-3 个方向不同的方案，用简短文字说明各自的特点和取舍：
- 每个方案一句话定位（如「聚焦输入」「双栏布局」「渐进展开」）
- 列出优势和适用场景
- 给出推荐理由

### 第三步：用 HTML 原型展示

**不要空谈设计，用原型说话。** 使用 html-prototype skill 生成可交互的原型。

多方案对比时：
- 用顶部 Tab 切换不同方案
- 每个方案都要可交互（点击、展开、弹窗都能用）
- 文件放在项目的 `public/` 目录下以便通过 dev server 访问

### 第四步：确认后改代码

用户选定方案后，用项目现有的设计系统实现，不引入新样式体系。

关键要求：
- **复用现有组件**：Button、Card、Textarea 等用项目里已有的
- **复用现有 token**：颜色用 `text-foreground`、`bg-primary/10` 等，不写 hex 值
- **保持一致性**：新做的页面要和产品其他页面风格统一

## 常见布局模式

### Composer 卡片（文本输入场景）

适合：AI 对话输入、需求描述、文章编辑等以文本为核心的页面。

结构：
1. 大 textarea（无边框，融入卡片背景）
2. 附件区（紧凑的图片/文件横排）
3. 底部工具栏（操作按钮 + 状态 chip + 提交按钮）

### 双栏布局（配置丰富的场景）

适合：配置项多且需要同时可见的场景。

结构：
- 左栏：核心内容输入
- 右栏：配置面板（sticky，跟随滚动）

### 渐进展开（折中方案）

适合：内容量中等、需要兼顾简洁和完整的场景。

结构：
- 核心输入在顶部
- 可选项用手风琴式折叠，标题行显示当前值摘要

## 注意事项

- 不要为了「设计感」而牺牲可用性
- 移动端适配：工具栏内容在窄屏时要能合理折叠
- 交互反馈：按钮有 hover 状态、展开有动画、选中有高亮
- 空状态：图片上传区为空时显示虚线框 + 图标 + 提示文字
