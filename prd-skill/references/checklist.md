# 质量自检清单

**使用方式**：Step 6，PRD 全文写完后逐条核对。P0 全部通过方可交付，P1 尽量通过，P2 视情况。

---

## P0 · 废稿级（任何一条不过 = 不能交付）

### 内容完整性
- [ ] 有明确的背景和目标，能用一句话说清楚为什么要做
- [ ] 每个操作都有具体的 Toast 文案（不能只写「提示成功」）
- [ ] 每个失败场景都有提示文案（上传失败、网络异常、权限不足等）
- [ ] 有边界与异常章节，每个主要功能至少覆盖一个失败路径
- [ ] 验收标准可测试、有明确触发条件和期望结果（不是「功能正常」）

### 结构正确性
- [ ] 功能范围明确——写了「不在本次范围内」的内容
- [ ] 同一个功能逻辑只写了一次（无重复描述）
- [ ] 复杂 PRD：末尾有数值约束汇总表

### 体量匹配
- [ ] 简单档没有超过 20 行正文
- [ ] 中等档没有超过 50 行正文
- [ ] 没有为了「看起来完整」而填充无意义内容

---

## P1 · 明显问题（影响可读性和可执行性）

### 写作规范
- [ ] 操作流程用箭头串联，没有把一句话的流程拆成 4 条列表
- [ ] 没有写 UI 布局（位置、尺寸、颜色、圆角）
- [ ] 没有写技术实现（API 参数、代码、数据库操作）
- [ ] 没有废话小标题（入口、规则、流程、说明）
- [ ] 空行符合规范（章节间 1 个，其他 0 个）

### 内容质量
- [ ] 有导出功能时，写了文件命名规则
- [ ] 多状态场景用了表格，而不是长段散文
- [ ] 引用其他章节时用了「详见 X.X」而不是重复描述
- [ ] 没有「已有能力」描述混淆前后端

### Triage
- [ ] 记录了去重搜索结果（无重复或列出相关项）
- [ ] 触发架构预审条件时已标注（新模块 / 新数据表 / 新 API endpoint）

---

## P2 · 最好有（提升文档质量）

- [ ] 有成功指标，且指标可量化（有基准值或目标值）
- [ ] 迭代增强类 PRD 明确写了「不变」的部分
- [ ] MVP 类 PRD 有「下一步扩展」方向
- [ ] 平台基建类 PRD 有接入方列表和非功能性要求
- [ ] 废弃下线类 PRD 有迁移方案和时间计划

---

## 常见错误速查

| 错误 | 正确做法 |
|------|---------|
| 跳过 Triage 直接开始写 | 先完成分类 → 去重 → 评估三步 |
| 每份 PRD 都套复杂结构 | 先选体量，简单需求用简单档 |
| Toast 只写「提示成功」 | 写具体文案：Toast「任务已删除」|
| 写「用户体验更好」作为指标 | 改为可量化：「操作完成率 ≥ 95%」|
| 在 PRD 里写按钮颜色位置 | 删掉，这是设计稿的工作 |
| 在 PRD 里写 API 参数 | 删掉，这是技术方案的工作 |
| 删除逻辑写了两遍 | 一处写完整，另一处「详见 X.X」|
