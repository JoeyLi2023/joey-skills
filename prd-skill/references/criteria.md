# 写作规则 · 验收标准指南

**使用方式**：Step 4 写内容时查阅，重点是写 AC 和功能描述时。字典式翻查，用完即放。

---

## 流程描述：按复杂度选写法

不要用一种格式统一所有场景。根据流程复杂度选择对应写法：

### 简单流程（2-3步，无分支）→ 一句话

```
✅ 点击删除，弹「确认删除？此操作无法撤回」，确认后 Toast「已删除」
```

### 有条件 / 有分支 → 缩进列表

```
✅ 点击提交：
   - 校验通过：保存，Toast「保存成功」
   - 校验失败：输入框边框变红，显示具体错误信息
```

### 多状态场景 → 表格

```
✅
| 状态     | 展示内容               | 可执行操作     |
|----------|------------------------|----------------|
| 处理中   | loading 横幅           | 无             |
| 成功     | 横幅消失，结果插入     | 在输入框编辑   |
| 失败     | Toast 报错文案         | 重试           |
```

**禁止**：用 `→` 串联超过 3 步的流程，或含分支条件的流程——`→` 只适合最简单的线性路径，其他场景下它用紧凑换了清晰。

## 验收标准（AC）写法

**原则**：一行一个条件，可测试，有明确的触发条件和期望结果。

**✅ 正确写法**
```
1. 输入框为空时点击提交，按钮不响应，输入框边框变红，提示「请输入{字段名}」
2. 名称超过 50 字符时，第 51 个字符无法输入
3. 删除成功后，列表移除该条目，Toast「已删除」2 秒后消失
4. 网络断开时点击提交，Toast「网络异常，请检查后重试」，表单数据不丢失
```

**❌ 错误写法**
```
1. 表单验证正常工作
2. 删除功能正常
3. 系统有良好的错误处理
4. 用户体验友好
```

**AC 覆盖清单**（每份 PRD 的 AC 必须包含）：
- 主流程成功路径（至少 1 条）
- 主要失败路径（至少 1 条）
- 边界值（字段长度上限、数量上限）
- 权限控制（如涉及）

## 禁止区（这些写了等于没写）

### 禁止写 UI 布局
不写位置、尺寸、占比、颜色、字体、圆角、阴影、间距。

**❌ 禁止**：「按钮居中显示」「左侧固定导航」「卡片圆角 8px」「主色调为蓝色」

**原因**：这是设计师的工作，PRD 写了反而限制设计自由度，且容易与最终实现不符。

---

### 禁止写技术实现
不写代码、API 参数、数据库操作、「携带 token」、「刷新列表」、「数据迁移」。

**❌ 禁止**：「调用 /api/delete 接口」「前端携带 userId 参数」「清空 Redis 缓存」

**原因**：这是工程师的工作，PRD 写了反而会被工程师质疑，且容易过时。

---

### 禁止写废话小标题
不写「入口」「规则」「流程」「说明」「注意事项」这类只是章节标签的小标题。

**❌ 禁止**
```
### 功能入口
用户可从首页进入该功能。

### 操作规则
用户需先登录才能使用。
```

**✅ 正确**：把内容直接写在上级章节里，不需要额外小标题包装。

---

### 禁止重复描述
同一个功能逻辑只在一个地方写完整，其他地方用「详见 X.X」引用。

**❌ 禁止**：删除逻辑在第 4.1 节写了一遍，在第 4.3 节又写了一遍。

**✅ 正确**：「删除逻辑详见 4.1」

---

### 禁止写显而易见的结果
不写「删除后列表更新」「成功后跳转」「点击取消关闭弹窗」这类工程师不需要被告知的内容。

---

### 禁止拆太细
能用一句话说完的不拆成多条，能用箭头串的不分列表项。

**❌ 禁止**
```
1. 用户点击保存
2. 系统校验数据
3. 校验通过后保存
4. 显示成功提示
```

**✅ 正确**：`点击保存 → 校验通过 → Toast「保存成功」`

---

## 多状态场景：用表格

有多个状态 × 多种展示 / 操作的场景，用表格比散文清晰。

```markdown
| 状态 | 展示内容 | 可执行操作 |
|------|---------|-----------|
| 处理中 | 进度条 + 百分比 | 取消 |
| 已完成 | 完成时间 | 下载、删除 |
| 失败 | 失败原因 | 重试、删除 |
```

---

## 空行规范

- 标题后：0 个空行
- 列表项间：0 个空行
- 章节间：1 个空行
- 表格前后：1 个空行
